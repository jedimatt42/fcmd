# js99er V9938 Initialization

This document describes how js99er initializes its V9938 emulation and how it
keeps the V9938 usable by TMS9918A-era TI-99/4A software. There are two
separate layers:

1. The V9938 device model's own reset state (`v9938.ts`).
2. A console-GROM patch (`patch_groms`) that fixes the console's default VDP
   register table before the console initializes the VDP.

The second layer is the direct equivalent of the EVPC DSR power-up register
initialization documented in `evpc.md`. js99er does not run an EVPC DSR; it
patches the console's 9918 default table so that the same table bases end up in
the first 16 KB of VRAM.

`TI994A.setVDP()` selects the implementation from the settings:

```ts
case 'V9938':
    this.vdp = new V9938(this.canvas, this);
    break;
case 'V9938/F18A':
    this.vdp = new V9938F18A(this.canvas, this, this.wasmService);
    break;
```

`TI994A.reset()` calls `this.vdp.reset()` along with the other devices. That
is the entry point for everything below.

## Reset sequence

For a plain V9938 (`v9938.ts`):

```ts
reset(): void {
    this.patch_groms(this.console.getMemory().getGROM());
    this.device_reset();
    this.canvas.width = V9938.HVISIBLE;
    this.canvas.height = 2 * V9938.VVISIBLE_NTSC;
    this.imageData = this.canvasContext.getImageData(...);
}
```

For the CaDD hybrid (`v9938-f18a.ts`):

```ts
reset(): void {
    // A hardware reset always returns the card to its default V9938 mode.
    this.f18aActive = false;
    this.latch = false;
    this.latchByte = 0;
    this.lastRegister57Value = 0;
    this.v9938.reset();       // patches GROMs and resets the V9938
}
```

So both V9938 modes patch the console GROM on every reset.

## The console-GROM patch

This is the important js99er-specific initialization:

```ts
private patch_groms(grom: GROMArray) {
    const vdpRegisterData = 0x0451;
    grom.setByte(vdpRegisterData + 2, grom.getByte(vdpRegisterData + 2) & 0x0f); // Name table
    grom.setByte(vdpRegisterData + 4, grom.getByte(vdpRegisterData + 4) & 0x07); // Pattern table
    grom.setByte(vdpRegisterData + 5, grom.getByte(vdpRegisterData + 5) & 0x7f); // Sprite attribute table
    grom.setByte(vdpRegisterData + 6, grom.getByte(vdpRegisterData + 6) & 0x07); // Sprite pattern table
}
```

### The console table

The TI console GROM contains the default VDP register table at GROM `>0451`:

```
GROM >0451: 00 20 F0 0E F9 86 F8 F7
             R0 R1 R2 R3 R4 R5 R6 R7
```

On a TMS9918A, the high bits of R2, R4, R5, and R6 are unused, so the console
can set them to 1. On a V9938 those bits are address bits:

| Register | 9918 use | V9938 use |
| --- | --- | --- |
| R2 | low 4 bits: name table | bits 6-0: name table A16-A10 |
| R4 | low 3 bits: pattern table | bits 5-0: pattern table A16-A11 |
| R5 | low 7 bits: sprite attribute | bits 7-0: sprite attribute A14-A7 (A16-A15 in R11) |
| R6 | low 3 bits: sprite pattern | bits 5-0: sprite pattern A16-A11 |

Left unpatched, `R2 =>F0`, `R4 =>F9`, `R5 =>86`, and `R6 =>F8` would move the
tables into high VRAM pages (well beyond the 16 KB a 9918-era program expects).

### After the patch

```
R2 = >F0 & >0F = >00
R4 = >F9 & >07 = >01
R5 = >86 & >7F = >06
R6 = >F8 & >07 = >00
```

The resulting R0-R7 table matches the EVPC DSR's R0-R7 values:

```
R0 = 00, R1 = 20, R2 = 00, R3 = 0E,
R4 = 01, R5 = 06, R6 = 00, R7 = F7
```

That gives the standard TI-99/4A memory map:

| Table | Address |
| --- | --- |
| Name table | `>0000` |
| Color table | `>0380` |
| Pattern generator | `>0800` |
| Sprite attribute | `>0300` |
| Sprite pattern | `>0000` |

The patch is idempotent: the masks only clear bits, so applying it on every
reset is harmless. It does not change R0, R1, R3, or R7.

### Why patch the GROM instead of the VDP?

The console's power-up GPL code writes the default table to the VDP. On real
hardware that code is fixed; a V9938 upgrade has to cope with it. The EVPC
does this with a DSR power-up routine that rewrites the same registers after
the console has run. js99er takes the simpler emulator route: it edits the
GROM table before the console reads it, so the console writes the correct
values itself. Both approaches arrive at the same register set.

## V9938 core reset state

`device_start()` allocates the V9938's VRAM and builds the palette:

```ts
this.vram_size = 0x30000;              // 192 KB (128 KB base + 64 KB expansion)
this.vram_space = new Uint8Array(this.vram_size);
// fill unavailable RAM with 0xFF if vram_size < 0x30000
this.palette_init();
```

`device_reset()` sets the register and status state:

```ts
this.offset_x = 8;
this.offset_y = 0;
this.visible_y = 192;

this.reset_palette();
for (i = 0; i < 10; i++) this.stat_reg[i] = 0;
this.stat_reg[2] = 0x0c;
if (this.model === V9938.MODEL_V9958) this.stat_reg[1] |= 4;
for (i = 0; i < 48; i++) this.cont_reg[i] = 0;

this.cmd_write_first = this.pal_write_first = 0;
this.int_state = 0;
this.read_ahead = 0;
this.address_latch = 0;
this.scanline = 0;

this.stat_reg[4] = 0xfe;
this.stat_reg[6] = 0xfc;

this.configure_pal_ntsc();
this.set_screen_parameters();
```

Key points:

* **All control registers R0-R47 are cleared to zero.** The emulator does not
  pre-load a 9918-compatible register set. That comes from the console GROM
  after the reset (with the patch above).
* Status register 2 starts at `>0C`; the unused high bits of S#4 and S#6 are
  set to 1, matching the V9938 data book and MAME.
* The palette is reset to the V9938 power-on palette, not to all black.
* `cmd_write_first` and `pal_write_first` are cleared, so the first control or
  palette byte after reset starts a new two-byte sequence.
* `address_latch` and `read_ahead` are cleared.
* PAL/NTSC and screen parameters are configured from the current register
  state (all zero at this point, i.e. NTSC, 192 lines).

### Power-on palette

`reset_palette()` uses the V9938 Technical Data Book palette:

```ts
const pal16 = [
    0, 0, 0,   // 0: black / transparent
    0, 0, 0,   // 1: black
    6, 1, 1,   // 2: medium green
    7, 3, 3,   // 3: light green
    1, 1, 7,   // 4: dark blue
    3, 2, 7,   // 5: light blue
    1, 5, 1,   // 6: dark red
    6, 2, 7,   // 7: cyan
    1, 7, 1,   // 8: medium red
    3, 7, 3,   // 9: light red
    6, 6, 1,   // 10: dark yellow
    6, 6, 4,   // 11: light yellow
    4, 1, 1,   // 12: dark green
    2, 6, 5,   // 13: magenta
    5, 5, 5,   // 14: gray
    7, 7, 7    // 15: white
];
```

The values are stored in G-R-B order internally. Each entry is written to the
palette registers and to the 16-color pen table. A separate 256-entry table is
built for Graphic 7.

If the console or a program does not load a palette, this is what a V9938
displays: the familiar 9918A-like colors, not an all-black screen.

## Port model and byte order

`memory.ts` defines the four V9938 write ports:

```ts
static readonly VDPWD = 0x8C00;  // VDP write data
static readonly VDPWA = 0x8C02;  // VDP set read/write address
static readonly VDPWP = 0x8C04;  // VDP write palette
static readonly VDPWC = 0x8C06;  // VDP write register indirect
```

The read ports are `>8800` (data) and `>8802` (status). `writeVDP()` dispatches
to the VDP interface:

```ts
case Memory.VDPWD: this.vdp.writeData(w >> 8); break;
case Memory.VDPWA: this.vdp.writeAddress(w >> 8); break;
case Memory.VDPWP: this.vdp.writePalette(w >> 8); break;
case Memory.VDPWC: this.vdp.writeRegisterIndirect(w >> 8); break;
```

In the V9938 class:

| Interface method | V9938 method | Purpose |
| --- | --- | --- |
| `writeData` | `vram_w` | write a byte to VRAM |
| `writeAddress` | `command_w` | address setup or direct register write |
| `writePalette` | `palette_w` | two-byte palette entry |
| `writeRegisterIndirect` | `register_w` | indirect register write via R17 |

### `command_w`: the V9938 two-byte protocol

```ts
command_w(data: uint8_t) {
    if (this.cmd_write_first) {
        if (data & 0x80) {
            if (!(data & 0x40)) {
                this.register_write(data & 0x3f, this.cmd_write);
            }
        } else {
            this.address_latch = ((data << 8) | this.cmd_write) & 0x3fff;
            if (!(data & 0x40)) {
                this.vram_r(); // read ahead
            }
        }
        this.cmd_write_first = 0;
    } else {
        this.cmd_write = data;
        this.cmd_write_first = 1;
    }
}
```

This is the V9938/MSX order:

* **Direct register write:** first byte = data, second byte = `>80|register`.
* **VRAM address setup:** first byte = address low, second byte =
  `A13-A8`, with bit 6 set for a write and clear for a read.

### `register_w`: indirect writes

```ts
register_w(data: uint8_t) {
    const reg = this.cont_reg[17] & 0x3f;
    if (reg !== 17) {
        this.register_write(reg, data);
    }
    if (!(this.cont_reg[17] & 0x80)) {
        this.cont_reg[17] = (this.cont_reg[17] + 1) & 0x3f;
    }
}
```

R17's bit 7 inhibits auto-increment; the low six bits are the target register.

### `palette_w`: two-byte palette entries

```ts
palette_w(data: uint8_t) {
    if (this.pal_write_first) {
        const indexp = this.cont_reg[0x10] & 15;
        this.pal_reg[indexp * 2] = this.pal_write & 0x77;
        this.pal_reg[indexp * 2 + 1] = data & 0x07;
        this.set_pen16(indexp, ...);
        this.cont_reg[0x10] = (this.cont_reg[0x10] + 1) & 15;
        this.pal_write_first = 0;
    } else {
        this.pal_write = data;
        this.pal_write_first = 1;
    }
}
```

The first byte carries red in bits 6-4 and blue in bits 2-0; the second byte
carries green in bits 2-0. R16 auto-increments after each pair.

### `vram_w`: address latch and R14 page wrapping

```ts
address = (this.cont_reg[14] << 14) | this.address_latch;
...
this.address_latch = (this.address_latch + 1) & 0x3fff;
if ((!this.address_latch) && (this.cont_reg[0] & 0x0c)) {
    this.cont_reg[14] = (this.cont_reg[14] + 1) & 7;
}
```

The 14-bit address latch increments on each data byte. When it wraps and the
mode bits in R0 request it, R14 (the 16 KB page register) increments. This is
what makes the V9938's 128 KB VRAM reachable while preserving the 9918's 14-bit
address behavior.

### Register writes and masks

`register_write()` applies the V9938 register masks, ignores registers above
46, and handles the special cases:

* R0/R1: update the display mode and interrupt state via `set_mode()` and
  `check_int()`.
* R9/R18: recalculate the horizontal offset.
* R15: resets the palette write latch.
* R20-R22: color burst registers, not emulated.
* R25-R27: V9958-only; forced to zero on a V9938.
* R44: CPU-to-VDP data transfer.
* R46: VDP command unit.

The mode is derived from R0/R1 exactly as in MAME:

```ts
n = (((this.cont_reg[0] & 0x0e) << 1) |
     ((this.cont_reg[1] & 0x18) >> 3));
```

### Contrast with the TMS9918A class

The TMS9918A implementation uses the older 9918 protocol: the first byte is
the address low byte, and the second byte carries the register number in bits
2-0 with bit 7 set. It stores the register value from the low byte of the
address register. Do not copy that logic into a V9938 implementation. The
V9938's register byte comes second and uses the low six bits as the register
number.

## CaDD V9938/F18A hybrid

`V9938F18A` emulates the CaDD V9938 Hybrid Video card. Its own header comment
states the behavior:

> The card powers up as a V9938, including TMS9918A compatibility. It watches
> for the F18A unlock sequence (writing a value with bits 0x1C set to VR57
> twice). When that sequence is seen, the card switches permanently to an F18A
> until the console is reset.

The wrapper holds a `V9938` and an `F18A`:

```ts
constructor(canvas, console, wasmService) {
    this.v9938 = new V9938(canvas, console);
    this.f18a = new F18A(canvas, console, wasmService, 'F18A', false);
}
```

The final `false` argument suppresses the F18A power-on splash: the card must
show V9938 output until the unlock sequence is seen.

`reset()` returns to V9938 mode and calls `this.v9938.reset()`, so the GROM
patch is applied in this mode too. While in V9938 mode, `writeAddress()` tracks
the two-byte sequence so it can detect a write to VR57 with the unlock bits:

```ts
if (!this.latch) {
    this.latchByte = i;
    this.latch = true;
} else {
    this.latch = false;
    if ((i & 0xc0) === 0x80) {
        register = i & 0x3f;
    }
}
this.v9938.writeAddress(i);
if (register === 57) {
    this.checkForUnlock(this.latchByte);
}
```

When the unlock is seen, `switchToF18A()` copies the V9938 VRAM into the F18A
and copies registers 0-7 across so the display does not change abruptly. The
hybrid is therefore a V9938 at power-up, exactly like the EVPC's 9918-compatible
mode, and only becomes an F18A when software explicitly unlocks it.

## Comparison with the EVPC DSR

| Aspect | EVPC DSR | js99er V9938 |
| --- | --- | --- |
| Compatibility mechanism | DSR power-up routine rewrites VDP registers | Patches console GROM default table before console init |
| Register table bases | R2=00, R3=0E, R4=01, R5=06, R6=00, R7=F7 | Same, after masking R2/R4/R5/R6 |
| Display mode | Graphics 1 / mode 0 | Graphics 1 / mode 0 |
| R8 | `>08` (128 KB VRAM) | Left at 0 by reset; console does not write R8 |
| R9 | `>02` (PAL default) then DIP/NOVRAM adjust | Left at 0 (NTSC, 192 lines) |
| R12-R19, R23 | Explicitly zeroed or set (`R12 =>F7`) | Left at 0 by reset; console does not write them |
| Palette | Loads EVPC default, grayscale, or NOVRAM palette | V9938 power-on palette |
| VDP port order | V9938 order (`>8C02` data then register; `>8C04` palette) | V9938 order (`command_w`, `palette_w`) |

Both approaches solve the same problem: the console's 9918-era default table
contains 1s in bits that are address bits on a V9938. The EVPC fixes the
registers after the console has written them; js99er fixes the table before the
console writes it. Neither one enables a V9938 bitmap or text mode; the VDP
stays in the 9918-compatible Graphics 1 layout.

The main practical difference for an emulator is that js99er's V9938 core
starts with R8-R23 all zero, while the EVPC DSR explicitly programs R8, R9,
R12, R16-R19, and R23. Software that relies on those registers being in a
particular state should program them itself rather than assuming a bare V9938
reset state.

## Notes for implementers

* A V9938 implementation must support the full four-port set:
  `>8800`/`>8802` for reads and `>8C00`/`>8C02`/`>8C04`/`>8C06` for writes.
  The EVPC DSR uses `>8C04` for palette data, not `>8C00`.
* The V9938 control port order is data-first, then `>80|register`. The EVPC
  DSR's `>44AA` helper produces exactly this sequence; it is not a 9918-style
  register write.
* The console GROM's default table must be masked before it reaches a V9938.
  This is the single most important compatibility fix, and it is what both the
  EVPC DSR and js99er's `patch_groms` accomplish.
* The V9938 power-on palette is already 9918-like; a missing explicit palette
  load does not mean a black screen.
* If emulating the EVPC card rather than a bare V9938, also implement the DSR
  page-selection CRU bits, the NOVRAM, the palette port, and the DSR bank
  loader. The VDP initialization itself is only the beginning of the card
  firmware.
